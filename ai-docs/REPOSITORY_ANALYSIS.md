# SlugcatPet 仓库分析报告

> 本文件是对仓库的整体分析，不属于项目运行文档。分析基于 2026-10-20 的 `main` 分支（版本 1.3.0）；2026-10-22 已合并上游 v1.3.2，2026-10-25 已合并 v1.3.3，除版本号和第 5.5 节外未重新统计。
> 验证方式：Git 历史与结构统计、逐模块静态阅读、`ruff check`、`ruff format --check`，以及在本机实际导入 Rain World 素材、启动应用、运行行为回归。实测环境与结果见第 5 节。

---

## 结论

这是一个完成度相当高的 Windows 桌面宠物项目：用 Python + PySide6 复刻《Rain World》蛞蝓猫的质点物理、行为状态机和皮肤系统。它不是玩具级 demo，而是有约 **4.1 万行有效代码**、数据驱动角色、行为回归基线、详细架构文档和发布合规检查的完整应用。

整体判断：**架构思路好、扩展性强、文档优秀；主要短板在测试可移植性、CI 缺失和少量历史耦合。**

## 1. 项目概况

| 项目 | 内容 |
|---|---|
| 定位 | Windows 10/11 桌面宠物，Rain World 粉丝项目 |
| 技术栈 | Python 3.12+、PySide6、numpy、Pillow、UnityPy |
| 入口 | `run_slugcatpet.py` → `slugcatpet.main:main` |

## 2. 运行链路

```
main.py
 ├─ QApplication / 单实例锁 / 托盘 / 全局热键
 ├─ 读取 ~/.slugcatpet/app.json（schema 2）
 ├─ 首次启动：SetupPanel 从 Rain World 安装目录提取图集、音乐、雨声
 └─ PetWindow
      ├─ 40Hz 固定物理 tick + 帧间插值
      ├─ 世界：水、雨、雪、无重力、暴风雪、物品
      ├─ PetUnit × N：身体 + 图形 + 能力 + 配件 + 行为状态机
      └─ 绘制：录制显示列表 + 局部重绘 + 静态内容签名
```

保存内容包括每只猫的体征、外观、性格、隐藏/死亡状态、猫际关系和场景物品；`keep_items` 开启时重启保留摆件，布局蓝图另有独立存取。

## 3. 架构拆解

核心目录职责清晰：

| 目录 | 职责 |
|---|---|
| `core/` | 两节质点身体、碰撞、游泳、尾巴、水中错位 |
| `abilities/` | 舌头、飞升、爆破、空翻、水生、重压、骨针 |
| `items/` | 果子、石头、矛、横竖杆、暖灯、黏菌、蝙蝠、蛋虫、珍珠 |
| `behaviors/` | 取果、爬架、发呆、游泳、生气、打猎、躲杀、定身、分享等 |
| `brain/` | 状态机、优先级规则、意图抽签、心情仲裁、手部管家、多猫协调 |
| `planning/` | 目标、够取方式、杆网图、A* 寻路、离线跳跃弧线 |
| `characters/` | 纯数据角色定义与严格校验 |
| `skins/` | Dress My Slugcat 皮肤解析、部位混搭、zip 安全解压 |
| `rendering/` | 图集、身体部件、尾巴、显示列表回放 |
| `audio/` | 音乐播放器、场景配乐、雨声、FSB→OGG/WAV 重建 |
| `platform/` | 置顶、全屏检测、挡雨窗口、vblank、单实例、自启动 |
| `ui/` | 设置、外观、HUD、音乐、雨计时器、珍珠编辑器等 |

最值得注意的设计是 **“能力 / 物品 / 行为 / 配件 / 角色”五类模块 + 注册表**：

- 角色 JSON 只声明“有哪些能力”和数值，不写具体行为。
- 行为通过 `requires` 匹配身体标签自动挂载；例如骨针能力移除 `mouth`，所有用嘴吃的行为自动不挂。
- 行为只认物品“用法”（`edible`、`throwable`、`climbable`…），不认具体物品种类。
- 共用动作留“技能槽”，能力可替换其中一步，例如舌头替换横杆上杆方式。
- 所有注册表都要求新模块加到末尾，保证原有猫的行为和绘制顺序不变。

这套设计让“加一只猫”基本只需要一个 JSON，“加一件物品”也只需要一个子目录加一行注册。

## 4. 设计亮点

1. **数据驱动且校验严格**  
   角色 JSON、能力参数、行为参数都有类型/范围/未知字段检查，配置写错会在启动时直接报错，而不是静默产生奇怪行为。

2. **行为扩展点设计成熟**  
   状态机有优先级分层、强制规则、意图效用抽签、心情权重、每 tick 回调、`swim`/`zerog`/`lie_down` 等扩展点，以及多猫占用/让路协调。新增行为不需要改核心状态。

3. **性能工程做得认真**  
   自定义显示列表录制/回放、按实际绘制范围局部刷新、静态内容签名、雪/雨独立定格、vblank 分频、自动帧率、省电慢档，这些都是桌宠长期驻留场景下的实用优化。

4. **测试思路适合物理模拟**  
   `tests/behavior_check.py` 用固定种子跑 4 个场景（共 20,900 tick），逐 tick 比对状态、位置、体力、好感、食物等，并对渲染帧做哈希；还额外断言“实际画到的像素必须在记录的刷新范围内”，能抓局部重绘残影。这个设计比普通单元测试更适合本项目的回归需求。

5. **文档与代码同步机制**  
   `ai-docs/ARCHITECTURE.md` 非常详细，包含 tick 顺序、优先级表、扩展接口和“还没模块化的部分”；`PARAMS.md` 由代码生成并可用 `--check` 校验；`arcs.json.gz` 也有离线生成/校验脚本。这种“文档可验证”的做法很少见。不过 `gen_arcs.py --check` 目前按压缩字节比较，跨平台会误报，见第 5 节。

6. **发布与合规意识**  
   仓库不含游戏素材；打包脚本会扫描产物，发现图集或音频文件直接中止，还检查彩蛋包泄漏；第三方许可随包携带；存档采用原子写；单实例锁、皮肤 zip 路径穿越/大小限制也都考虑到了。

7. **基础代码整洁**  
   实际运行 Ruff：`ruff check .` 全部通过，`ruff format --check .` 显示 266 个文件已格式化；所有 Python 文件都有模块 docstring。对于这个体量的个人项目，这一点很突出。

## 5. 实际运行检查（2026-10-20）

环境：Python 3.12.15、PySide6 6.12.0、UnityPy 1.25.4、numpy 2.5.4、Pillow 12.3.0；Linux x86_64，Qt 使用 offscreen 平台；Rain World 安装在 `/mnt/Data/Game/SteamShareLinux/steamapps/common/Rain World/`。

### 5.1 依赖与素材导入

- 四个依赖均可正常导入，`uv run` 直接使用项目虚拟环境。
- `python -m slugcatpet.gameassets "<游戏目录>"` 成功导入 `rainWorld`、`rainworldmsc`、`uiSprites`、`uispritesmsc` 及 `waterSprites`，并写入 `game_path.txt`。
- 用临时用户目录启动应用 10 秒，应用没有崩溃；期间后台补提取了 4 首场景曲、7 个雨声和 9 个业力音效，完整素材约 38 MB。offscreen 模式下的 `This plugin does not support raise()` 和托盘信号警告来自 Qt 平台插件，不是应用异常。

### 5.2 静态门禁

| 检查 | 结果 |
|---|---|
| `uv run ruff check .` | 通过 |
| `uv run ruff format --check .` | 通过，329 个文件已格式化 |
| `uv run python tools/params_doc.py --check` | 通过，`ai-docs/PARAMS.md` 是最新的 |
| `uv run python tools/gen_arcs.py --check` | **失败**，但解压后的 JSON 与仓库内容完全一致 |

`gen_arcs.py --check` 的失败是跨平台误报：原文件与新文件的 gzip 头第 9 字节分别是 `0x0a` 和 `0x03`（gzip 的 OS 字段），压缩后的字节不同，但 `gzip.decompress()` 后的内容逐字节相同。也就是说弧线数据没有过期，校验方式本身不可移植。

### 5.3 行为回归

`uv run python tests/behavior_check.py check`，四个场景并行，总耗时约 5.1 秒：

| 场景 | tick | 物理结果 | 帧哈希结果 |
|---|---:|---|---|
| `items` | 5,000 | 一致 | 83 / 100 帧不同，首个不同在 tick 700 |
| `env` | 4,500 | 一致 | 87 / 90 帧不同，首个不同在 tick 0 |
| `cursor_play` | 5,400 | 一致 | 108 / 108 帧不同，首个不同在 tick 0 |
| `trouble` | 6,000 | **tick 3437 首次分歧** | 因物理先失败，未继续比帧 |

`trouble` 的分歧是 pet 1 的 `c0.x`：基线 510.587，本次 510.341；同一 tick 的状态、动画、y 坐标、体力、好感、食物、寒冷都相同。它发生在 tick 3420 触发杀猫弹窗、舌头进入 `DodgeKill` 之后，属于很小的数值偏移。合理推测是 Windows 与 Linux 的数学库/浮点路径差异在多次状态切换后累计，跨过了测试的 3 位小数舍入；也可能是该分支某个尚未覆盖的确定性差异。需要在 Windows 上用同一份代码复跑确认，不能仅凭这次结果判定为行为回归。

帧哈希大面积不同则基本可以确定是渲染环境差异：测试对整张 1920×1080 窗口取 MD5，Qt 版本、平台插件、字体/抗锯齿都会改变像素。仓库本身也把运行要求限定为 Windows 10/11，因此 Linux offscreen 的帧结果不能直接当作回归失败。

### 5.4 结论

- 依赖、素材导入、应用启动链路是通的，项目可以在当前环境跑起来。
- 代码质量门禁里 Ruff 和参数文档通过；弧线校验需要修成“解压后比较”。
- 行为回归的物理部分在 4 个场景中 3 个完全一致，1 个出现单点数值分歧；渲染部分在非 Windows 环境不可用。测试设计本身有效，但当前基线不具备跨平台可重复性。
- 由于没有 Windows 环境和真实桌面会话，托盘、置顶、全局热键、透明窗口等平台相关功能仍未做最终验证。

### 5.5 v1.3.3 合并后复查（2026-10-25，真实 KWin Wayland 会话）

- 全量 61 个单元测试、Ruff、格式检查、`params_doc --check` 均通过；`node --check` 同时检查几何脚本和快捷键脚本。
- `items`、`env`、`cursor_play` 的物理状态逐 tick 与基线一致，仍只有平台相关的渲染帧哈希差异；`trouble` 的已知绘制边界误报未变。
- 全局快捷键在 KWin 6.8 Wayland 真机验证：meow、HUD、freeze、quit 均能触发；改键后旧键位释放、新键位生效，应用重启后回调仍正常。
- Lizard Pet 可在本机 Wayland 会话启动，KWin 几何/快捷键脚本加载成功，蜥蜴音效素材已存在；视觉和首次启动素材提取 UI 仍待人工验收。

## 6. 风险与问题

| 优先级 | 问题 | 说明 | 建议 |
|---|---|---|---|
| **P1** | 行为回归测试不可移植 | 实测：四个场景全部未通过。其中 `items`、`env`、`cursor_play` 物理一致但帧哈希分别有 83/100、87/90、108/108 帧不同（Linux/Qt 6.12）；`trouble` 在 tick 3437 出现 0.246 px 的物理分歧。`_setup_env` 还依赖 `~/.slugcatpet/assets`，干净环境/CI 无法运行；帧哈希是整窗 MD5，Qt 版本、平台、字体抗锯齿差异都会导致失败 | 增加“合成图集”测试夹具；拆分 `--physics` / `--frames` 模式；按平台记录基线；在 Windows 上复跑确认 `trouble` 的单点分歧 |
| **P1** | 没有 CI | 仓库没有 `.github/workflows`，Ruff、参数文档、弧线校验、行为回归都靠手动 | 加一条最小 CI：Ruff + `params_doc --check` + 修正后的 `gen_arcs --check`；Windows job 跑行为检查 |
| **P2** | `gen_arcs.py --check` 跨平台误报 | 实测在 Linux 上报告“已过期”，但解压后的弧线 JSON 与仓库完全一致；原因是直接比较 gzip 压缩字节，Python/zlib 在 Windows 和 Linux 上写出的 gzip OS 字段不同（偏移 9：`0x0a` vs `0x03`） | 将校验改为比较 `gzip.decompress()` 后的内容，或比较解压后 JSON 的规范化字节 |
| **P2** | 隐藏猫生命周期不完整，存在丢猫风险 | `add_pet()` 只检查可见猫数量（`window.py:1089`），隐藏猫不占上限，反复“隐藏→新增”可让 `all_pets()` 超过 20；读档时 `_build_pets()` 又只恢复前 `MAX_PETS` 只（`window.py:247`），超出的隐藏猫会静默消失。另外 `_reground()` 只遍历 `self.pets`（`window.py:737`），隐藏猫在分辨率变化后可能没有更新身体边界 | 给“可见 + 隐藏”设总上限，或读档时恢复全部隐藏猫；`show_pet()`/工作区变化时也重建隐藏猫的尺寸和地面 |
| **P2** | 配置损坏会静默重置 | `_load_params()` 捕获所有异常后返回 `{}`（`main.py:82-90`），随后自动保存会覆盖原文件，用户设置和存档可能丢失 | 损坏时先备份为 `app.json.bak`；加 schema 校验和用户可见提示 |
| **P2** | 核心文件偏大、隐式耦合 | `core/creature.py` 1837 行、`window.py` 1504 行、`main()` 346 行；世界状态直接挂在 QWidget 上；`PetUnit.__getattr__` 把未知属性全部转发给窗口（`petunit.py:71-75`），而 `BehaviorFSM` 的参数名叫 `window`、实际是 `PetUnit`，读代码时很容易误解 | 先抽 `World`/`Scene` 对象；把 `fsm.win` 显式改名为 `pet`；用 `PetContext` 替代万能 `__getattr__`；逐步拆 `creature.py` |
| **P3** | UI、存档、皮肤、音频缺少自动化测试 | 目前只有行为回归；`ui/` 约 6,776 行，设置/外观/珍珠编辑器等没有测试 | 用 `pytest-qt` 或 offscreen 脚本做面板创建、存档往返、皮肤 zip 安全解压的 smoke test |
| **P3** | 异常捕获偏多，可观测性不足 | 约 58 处 `except Exception`、约 60 处 `except: pass`，多数是平台兼容的防御性代码，但资产提取、存档、皮肤加载的真实错误也可能被吞掉；打包成 windowed exe 后 `print` 看不到 | 统一日志到 `~/.slugcatpet/log.txt`，错误弹窗只展示可操作信息 |
| **P3** | 类型与静态检查覆盖有限 | 约 17% 的函数有返回类型标注；Ruff 只启用 `E4/E7/E9/F`，没有 import 排序、bugbear、类型检查 | 核心物理/规划模块逐步加类型；Ruff 先加 `I`、`UP`、`B`，再考虑 mypy/pyright |
| **P3** | 文档以中文为主 | `ai-docs` 全中文，英文 README 已说明；非中文贡献者上手成本较高 | 至少补一份英文架构概览和扩展指南 |

另外，完整 assets 目录约 38 MB，行为回归每次会把它整体复制到临时目录（包括音乐），四个场景并行时磁盘和 I/O 开销不小；建议只复制图集文件。

## 7. 建议的改进顺序

1. **先把回归测试搬到 CI**：Ruff、参数文档是零成本门禁；先修 `gen_arcs --check` 的压缩字节比较，再把弧线校验加进去；行为检查用合成图集和“物理/帧”分层模式解决可移植性。
2. **修隐藏猫问题**：统一“总猫数”上限，读档不截断隐藏猫，工作区变化时 `_reground` 覆盖 `all_pets()`。
3. **加日志和存档备份**：这是桌面应用面对真实用户时最划算的稳定性投入。
4. **逐步解耦**：先抽 `World`，再改 `fsm.win` 命名，最后拆 `creature.py`；不要一次性大重构，因为行为基线会提供安全网。
5. **补 UI/存档/皮肤的 smoke test**，再考虑更严格的静态检查。
6. **在 Windows 上复跑完整回归**，确认 `trouble` 的 tick 3437 分歧是平台差异还是真实回归。
